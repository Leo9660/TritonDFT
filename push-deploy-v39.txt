# WHAT'S IN v39 (commits 0af6219..9335b2e, i.e. everything after v37)
# -----------------------------------------------------------------------------
#  PERF  32 MPI ranks per job (was 8) + k-point pools (-nk 8).
#        Measured on 6-atom MoS2: 8->32 ranks alone was only 2.1x, but 3.8x with
#        pools, because k-points parallelise almost linearly while the FFT work
#        does not. MoS2 vc-relax should go 28 min -> ~7-8 min.
#  FEAT  User-selectable pseudopotentials (functional / relativistic / accuracy).
#        HARD-ENFORCED by patching pseudo_dir in the generated input, not by
#        prompt injection — the model cannot override the user's choice.
#        The choice IS also shown to the model, because it constrains cutoffs
#        (stringent needs a higher ecutwfc) and decides whether SOC is possible.
#  FIX   Coordinate precision. The model was writing 0.6667 where the value is
#        2/3 — a 3.3e-5 error, above QE's symmetry tolerance (accep = 1e-5).
#        That cut detected symmetry ops 24 -> 8 and inflated the irreducible
#        k-points ~40 -> 129, i.e. a ~3x slowdown from rounding alone.
#  FIX   Magic-link sign-in returned 422 for EVERY user. FastAPI treats a bare
#        `str` parameter as a QUERY param, so the frontend's JSON body was
#        rejected. Now a Pydantic body model. (This is the login bug.)
#  FIX   ph.x retry inherited stale _ph0 recovery state -> "wrong ldisp".
#  FIX   Parser looked for the old output_N_M.out names after the rename.
#  FIX   Post-processing tools (dos.x/projwfc.x/q2r.x/matdyn.x/dynmat.x) were
#        generated with ZERO format guidance — fn_section never reached the
#        prompt.
#  FEAT  Task-oriented filenames, immutable retry attempt dirs, scratch cleanup.
#  CHORE Default model gpt-4o -> gpt-5.2.
#
# NOT in this image: the chat frontend. It deploys to GitHub Pages from
# TritonDFT-chat and is already live (44c4101).

# RISK — read before deploying
# -----------------------------------------------------------------------------
# 8 replicas x 32 CPU limit = a 256-core burst ceiling in one namespace, on
# priorityClassName: opportunistic. Requests stay at 4 (so 32 cores guaranteed
# total, which schedules fine) but the burst headroom is now 8x the request,
# up from 4x. Two consequences:
#
#   1. NRP policy. We already run afoul of two of their usage policies and have
#      no fixed core allocation; a 256-core burst makes us more visible, and
#      opportunistic pods are the first thing culled. If workers start getting
#      evicted after this, the CPU limit is the first thing to lower — try
#      cpu: 16 and QE_NK 4 before blaming anything else.
#
#   2. CFS throttling. On a busy node the limit is aspirational: the kernel
#      throttles back toward the 4-core request. The 3.8x speedup was measured
#      on a quiet node and is a best case, not a guarantee.
#
