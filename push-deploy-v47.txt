# NOT IN THIS RELEASE, and worth being explicit about: continuing a calculation
# from an earlier one. "Now compute the DOS for the same material" is triaged as
# "calculate" and starts over — a fresh Materials Project lookup and a fresh
# relaxation. A follow-up can READ the earlier run's files, but nothing carries
# its charge density or relaxed geometry forward.
#
# New since v46:
#
#  FIX  Granting a user CPU access still ran their jobs script-only.
#       v46 added the can_use_cpu column, the admin control and the /me field —
#       but not the line that actually authorises a run:
#           privileged = user.is_admin or user.is_unlimited
#       So the flag was set, the frontend enabled its toggle and sent
#       script_only=false, and this quietly forced it back to true. The user saw
#       a working switch and a script-only run, with nothing explaining it. It
#       now includes can_use_cpu. (The separate in-flight job cap deliberately
#       does not: that flag says what you may run, not how many at once.)
#
#  FEAT ⚠️ A message is triaged BEFORE anything runs.
#       Every message used to start a Materials Project lookup and a full DFT
#       workflow — including "what was that band gap again?", which re-ran a
#       calculation to answer a question already answered and read to a chemist
#       as the tool not listening.
#
#       A cheap classification call now sorts each message into:
#         calculate — needs a new run; proceeds exactly as before
#         followup  — asks about work already done; answered from the
#                     conversation, no MP and no QE
#         chat      — a general DFT question; answered directly
#         offtopic  — declined in one sentence
#
#       It FAILS OPEN: a parse error, an unknown label or an empty answer all
#       fall back to "calculate", because refusing a real request is worse than
#       running a needless one.
#
#       For this to work the worker needed the conversation, which it never had
#       — it only ever received the single user message. jobs.context now
#       carries a trimmed transcript (6 turns, 12k chars, keeping the END of
#       each assistant turn since the analysis and numbers are written last).
#
#  FEAT A follow-up can READ the run's files, not just re-read the chat.
#       The conversation text holds the streamed log and nothing else, so
#       "what cutoff did step 3 use?" was unanswerable with 03_nscf.in sitting
#       on disk. Rather than widening the context until everything fits, the
#       follow-up is given a MANIFEST — every job in this chat, what it
#       concluded, and what files it left — and asks for what it wants:
#         {"action":"read","files":[{"job":"...","name":"02_scf.in"}]}
#         {"action":"answer","answer":"..."}
#       Bounded at 2 rounds, 4 files and 60 kB, because a vc-relax .out is
#       routinely over 150 kB. Filenames go through is_safe_filename and the
#       job must appear in a manifest already filtered by user_id, so a
#       requested "../../etc/passwd" is dropped. If the loop produces nothing
#       it falls back to the one-shot answer, and then to running a real
#       calculation.
#
#       This needs jobs.conversation_id: the worker had no way to find the
#       earlier runs of the same chat. It is client-supplied and opaque, and
#       every lookup is still filtered by user_id, so it grants no access on
#       its own.
#
#  ⚠️ DATABASE MIGRATION: jobs.context (ALTER TABLE ... ADD COLUMN IF NOT
#       EXISTS, additive, v46 pods ignore it — rollback needs no undo), plus
#       jobs.conversation_id and its index, on the same terms.
#
# Also new since v45 was pushed:
#
#  FEAT The run STATES which pseudopotential library it used. (0be522b)
#       Under auto the settings panel can only show the fallback, and the
#       request or the model may have chosen otherwise — so nothing on screen
#       said what a run actually ran with. The agent now prints
#         [pseudo] Library for this run: PseudoDojo PBEsol · SR · standard
#                  (from your request)
#       as soon as the FIRST step fixes pseudo_dir, which is the vc-relax step
#       in any workflow that has one. The frontend shows that line in the
#       settings card in preference to the panel's own setting, and says
#       "library not settled yet" until it arrives rather than implying the
#       fallback is the answer.
#
# Everything from the v45 list, restated:
# -----------------------------------------------------------------------------
#  FIX  restart_mode is repaired, not rejected. (98cc518)
#       NEW_STEP_RESTART_MODE_INVALID fired on nearly every nscf/bands step,
#       cost a full regeneration round each time, and printed an ERROR the user
#       read as a failure. A step the agent has just written has no checkpoint
#       of its own to resume from, so 'from_scratch' is the only correct value —
#       always, with no judgement involved. force_from_scratch() now rewrites it
#       in place BEFORE validation runs, so the rule never fires.
#
#  FIX  Raman under GGA no longer loops forever. (c5705ac)
#       RAMAN_NOT_IN_THIS_PH demanded lraman=.true. whenever the query mentioned
#       Raman, with no knowledge of the functional. Under PBE that was
#       unsatisfiable: lraman off -> validator rejects; lraman on -> ph.x aborts
#       with "third order derivatives not implemented with GGA". The agent
#       oscillated until it ran out of retries, each attempt a full 32-rank ph.x
#       launch. (The MPI_ABORT in those logs is how QE reports a fatal error
#       under mpirun — it was never a parallelism problem.) The rule now reads
#       the run's XC family from the pw.x inputs beside the ph.x one and fails
#       ONCE with RAMAN_REQUIRES_LDA, naming both ways out.
#
#  DOC  tool_requirements explains what restart_mode is NOT. (f81c52d)
#       Cannot improve correctness — the repair above already guarantees the
#       value — but a model that writes 'restart' for an nscf step believes that
#       is how a step inherits the SCF charge density, and that belief distorts
#       other parts of the input the repair does not touch.
#
#  FIX  The MP spacegroup note is out of the user stream. (56748e0)
#       "spacegroup_symbol='P63/mmc' would 500; querying by number 194" was
#       written for me. The Materials Project API really does return 500 for any
#       spacegroup symbol containing a slash, and querying by international
#       number is the equivalent workaround — but that is a pod-log detail.
#
#  FIX  Plot files the prompt sanctioned but the parser could not find.
#       (6a08a21) tool_requirements offered filband='<prefix>.band' "or a fixed
#       name 'bands.dat'", and fildos='<prefix>.dos' "or 'dos.dat'" — while
#       parse_bands globbed only *.band.gnu and parse_dos only *.dos. A model
#       taking the second, equally sanctioned option produced bands.dat.gnu and
#       dos.dat, and the plot silently vanished while the run reported success.
#       Parsers now fall back, so runs ALREADY on disk with those names start
#       plotting without being re-run; the prompt no longer offers the choice.
#
#  FIX  relaxed_structures paired the wrong material with the wrong index.
#       (ffeef35) Used `mid` — whatever the selection loop ended on — instead of
#       `min_id`, and indexed a single Structure as if it were a list. Nothing
#       reads the field today, which is why it never surfaced; the planned
#       "start from the MP relaxed structure" option reads exactly this.
#
#  FIX  The final answer contradicted the result card beside it. (e9c73f2)
#       One MoS2 run showed a "Band gap 1.218 eV" card and, on the same screen,
#       a conclusion saying the gap "was not extracted... so I cannot state the
#       band gap" — and reported a total DOS "written to system_1.dos.dat" when
#       dos.x had written nothing. _final_answer() saw only the per-step prose:
#       the numbers come from extract_result(), which the worker runs AFTER the
#       agent returns, and nothing told it which plottable files exist. It now
#       reads the run directory itself first, and the prompt names that section
#       the authority on outcomes.
#
#  FIX  ⚠️ THE WRONG SILICON. Every "Si" run was computing a metastable
#       polymorph, not diamond silicon.
#
#       tool_mp truncated the candidate list to `limit` (25) and THEN picked the
#       lowest energy_above_hull. MP returns "Si" as 43 entries in no particular
#       order, so 18 were dropped before the minimum was taken — and the ground
#       state (mp-aaaaaaft, Fd-3m, 2 atoms, ehull=0) was among the dropped ones.
#       What survived and won was C2/m (#12), 8 atoms, 0.082 eV/atom above the
#       hull. Verified against the live API: the fix now returns mp-aaaaaaft.
#
#       energy_above_hull is now fetched with the search and the candidates are
#       sorted by it BEFORE truncation. This also removes one API round trip per
#       candidate — the old code re-queried each id for a number the search had
#       already returned.
#
#       The material card now also states the hull energy — "ground state", or
#       "ehull 0.082 eV/atom" when it is not. The selection rule is invisible
#       until it goes wrong, and when it did there was nothing on screen to
#       contradict it.
#
#       This also explains the slow, aborting Si runs: an 8-atom triclinic cell
#       (γ=148.9°) has far more irreducible k-points than 2-atom diamond Si at
#       the same 8×8×8 mesh, and a metastable Si is a poor match for the
#       occupations='fixed' a gap workflow asks for.
#
#  FIX  ⚠️ "Something went wrong" with no detail, under two concurrent users.
#       The chain, end to end:
#         one user triggers a blocking handler (a PVC listing, a zip)
#         -> the event loop is held (see the next item)
#         -> /healthz is served by that same loop and cannot answer within the
#            probe's default timeoutSeconds=1
#         -> three failures and kubelet KILLS the API pod
#         -> every in-flight request on it is reset, fetch rejects, the frontend
#            gets code "unknown" and shows the generic message.
#       The event-loop fix below removes the cause. The liveness probe is also
#       slackened (timeoutSeconds 5, failureThreshold 6) because restarting a
#       merely-busy pod is worse than waiting for it. And the frontend no longer
#       throws away the underlying text — "unknown" is a registered i18n key, so
#       tr() was replacing "Failed to fetch" with "Something went wrong".
#
#  FIX  ⚠️ WORKSHOP-CRITICAL: the per-IP rate limit was 20/minute for the whole
#       ROOM. slowapi keys on the client IP, and everyone on one wifi shares one
#       NAT address — so twenty requests a minute was the budget for all
#       attendees combined, not per person. Now 180/minute; 5000/day. Credits
#       remain the real spend limiter, which is what that comment always said.
#
#  PERF ⚠️ Every API endpoint was blocking the event loop.
#       All 23 handlers across jobs.py, admin.py and auth.py were declared
#       `async def` while doing entirely blocking work — synchronous SQLAlchemy
#       queries, and for the artifact routes iterdir/stat/read over a shared
#       PVC. FastAPI runs a `def` handler in its threadpool but an `async def`
#       one directly on the event loop, so with uvicorn's single loop per pod
#       ONE slow directory listing stalled every other request on that pod,
#       including the /jobs/{id} polling the entire run view depends on. Not one
#       of the 23 awaits anything, so nothing was gained by it.
#
#       They are `def` now. Effective concurrency per API pod goes from 1 to 10.
#       The threadpool is pinned to 10 at startup to match pool_size +
#       max_overflow: each in-flight request holds a session for its whole
#       duration, and anyio's default of 40 threads against 10 connections would
#       trade event-loop stalls for connection-pool timeouts.
#
#  FEAT ⚠️ BEHAVIOUR CHANGE: pseudopotentials are chosen by the agent BY DEFAULT.
#       The dropdowns used to be unconditionally binding, so "use PBEsol" in a
#       prompt did nothing and nothing on screen said why. (Kuntal's point.)
#
#       Resolution order under the new default, "auto":
#         1. The request names a functional -> the existing regex picks that
#            library, including switching to FR when SOC is asked for.
#         2. It names none -> NOTHING IS PATCHED. Whatever pseudo_dir the model
#            wrote in its own script survives. The prompt now lists the exact
#            absolute paths installed on this host, since the model cannot know
#            them, and _guard_pseudo_dir() replaces anything that is not one of
#            them rather than letting a run die on a missing directory.
#         3. The dropdowns are only the fallback, and are greyed out in the UI.
#
#       "manual" is the other mode and is unchanged: the dropdown is binding,
#       and a library named in the prompt is ignored — but the log now SAYS it
#       was ignored and names the setting that overrode it.
#
#       input_dft is no longer forced to the dropdown's functional under auto.
#       Forcing it while the model picked its own library made the two
#       contradict and tripped PSEUDO_XC_MISMATCH on every step.
#
#       pseudo_choice now carries "mode"; unknown values fall back to manual.
#       An OLD frontend sends no mode at all and therefore keeps today's
#       behaviour, so the two can be deployed in either order.
#
#  FEAT New endpoint GET /jobs/{id}/steps/{n}/input, for the UI's input tab.
#       The UI used to list the whole run directory and filter client-side —
#       iterdir plus a stat per file over a PVC eight workers are writing to,
#       slow enough that the tab appeared to hang. A glob for the step's own
#       prefix touches almost nothing. Frontend already deployed.
#
#  FIX  A band-gap workflow silently produced a meaningless DOS. (f6fe81d)
#       Three faults in a row, the first ours by construction:
#         1. A gap needs occupations='fixed' on the nscf. A 'fixed' run stores
#            no broadening, so dos.x read degauss=0.0 — and the prompt told it
#            to use bz_sum='smearing'. A Gaussian sum of zero width does not
#            error: JOB DONE, full-length file, every value meaningless. Our
#            recommended way to get a gap and our recommended way to get a DOS
#            could not both be followed. &DOS now sets ngauss=0 and an explicit
#            degauss=0.01 in that case (degauss is Ry; Emin/Emax/DeltaE are eV).
#         2. .dos was not in USEFUL_EXTS, so qerun.dos was invisible in the file
#            list and absent from the zip — it looked like it was never written.
#            Nor were projwfc.x's outputs, whose "extension" is #3(d): every
#            projected-DOS file was hidden. Names are matched now too.
#         3. NaN survives float() and reaches the SVG path, rendering an empty
#            box rather than nothing. Non-finite rows are dropped.
#
#  Frontend since v42 is already live on Pages (plan list now renders, per-step
#  input/output tabs, conversation opens at its end, no failure styling on a
#  step that is still running). Not in this image.
#
#  NO database migration in this release. NO dependency changes.

# ⚠️ RESOURCE CHANGE IN THIS RELEASE — read before applying k8s/worker.yaml
#      JOB_NP          32 -> 8     ranks now equal the GUARANTEED cores
#      QE_NK            8 -> 0     pools measured to do nothing at this size
#      requests.cpu     4 -> 8     the scheduler now promises what we launch
#      limits.cpu      32 -> 16    burst headroom, not a target
#      replicas         8 (unchanged) — concurrency is not reduced
#
#      Reserved total goes 32 -> 64 cores. Still placeable on an opportunistic
#      priority class; 8 x 32 = 256 would not have been.
#
#      Why: runs reported 11.6s CPU against 26.8s wall — more than half the time
#      descheduled, because 32 ranks were launched against a 4-core guarantee,
#      paying the communication cost of 32 for the throughput of 4. Measured on
#      diamond Si, 8 ranks is 0.89s and 32 is 0.60s, while the harness around
#      each step costs ~30s. There was nothing to buy up there.
#
#      If workers start going Pending after this, the reservation is the cause:
#      drop requests.cpu and JOB_NP together, never one without the other.
